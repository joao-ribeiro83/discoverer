## 1. What is already done, and what is left

The lexer and parser are **complete** and always were. `parseFormulaTree`
(`migrate/src/services/workbook-parser.ts:1094`) is a recursive-descent reader for the
whole grammar, and it reads all 22 748 distinct corpus formulas with **0 parse failures
and 0 `unknown` nodes**. It was called `parseConditionTree` until this stage; the rename
(review A-10) is cosmetic but load-bearing for whoever greps for it next.

What was missing is the **renderer**, and behind it the fixity table it needs. This stage
produced that table. Phases 4.2 onward write the renderer.

## 2. The grammar

```
node    ::= '[' field { ',' field } ']' [ '(' [ node { ',' node } ] ')' ]
field   ::= integer | '"' string '"'
```

A string field honours backslash escapes. No workbook in the source EUL exercises one —
none of its 3 395 token strings contains a backslash — so escape handling is tolerance,
not a confirmed encoding.

**Conditions and calculations are one language.** Same namespaces, same grammar, same
parser. Any design that treats them as two is wrong.

### The five namespaces

Exactly five, matching the parser's switch with no missing case. Counts below are
weighted occurrences **in the aligned corpus**, which is a different denominator from the
whole-dump counts in `formula-decoder-analysis.md` — see §11.

| Namespace | Meaning | Aligned uses | Resolved from |
| --- | --- | --- | --- |
| `[1,n]` | built-in function or operator | 224 398 | `EUL_FUNCTION_NAMES` (222 entries) |
| `[5,k,"…"]` | literal of kind `k` | 143 160 | inline |
| `[6,n]` | item reference | 129 725 | workbook element table (`IoId`) |
| `[8,n]` | parameter reference | 3 864 | workbook element table (`IoId`) |
| `[2,n]` | custom PL/SQL function | **0** | workbook element table (`IoId`) |

`[6,n]` ids run 16–1461 (1 345 distinct); `[8,n]` ids run 17–1456 (258 distinct). Both are
**workbook-local `IoId`s**, not EUL ids. The EUL id is reached after the element-table
indirection.

The `[2,n]` zero is not a typo. See §9.

## 3. The `[1,n]` code table — how it was fitted

`DisplayFormula` is **Oracle rendering its own token string**, paired 1:1 with it. So
fixity is observable: render the tree under a hypothesis and ask whether Oracle's text
could have come out of it. This is fitting, not research (D-052).

**Method** — `migrate/src/scripts/fit-builtin-codes.ts`:

1. Each candidate shape (prefix, infix tight, infix spaced, bracket, between, in-list,
   when-then, case-end, passthrough, …) is turned into a regular expression over the
   token tree.
2. An identifier leaf becomes a capturing placeholder, back-referenced on its second and
   later use in the same formula. That back-reference is a real constraint: a hypothesis
   that renders one item two different ways cannot match. A placeholder may not open or
   close on a space, which is what separates `a<b` from `a < b`.
3. **Constraint propagation.** A row is evidence for a code only once every *other* code
   in it is settled. Round 1 fits codes that appear alone; each later round fits codes
   whose row has one unknown left; stop at the fixed point.
4. Two placeholder classes. `strict` forbids brackets and commas; `loose` allows them,
   because a `[6,n]` leaf is sometimes another calculation that Oracle expands in place
   (§8). Strict is tried first and the table records which settled each code.

**The settling rule.** A row counts against a shape *only if some other candidate shape
explains it*. A row that no hypothesis at all can produce is not evidence about fixity —
it is a damaged row (§11) — and it is counted and reported as `unexplained` rather than
allowed to vote. This is not circular: evidence that contradicts the winner by matching a
rival is never discarded, so a wrong shape cannot silence the case against it.

### Reading this table correctly — the one trap

**A `Shape` is how Oracle DISPLAYS the node. It is not the SQL to emit.** The display form
is the oracle for *structure* — arity, fixity, argument order — and nothing else. Three
rows prove the point:

- `[1,117]` displays as `COUNT_DISTINCT(a)`. The SQL is `COUNT(DISTINCT a)`.
- `[1,111]` `ROWCOUNT` takes no arguments and displays as `COUNT(*)` — the fitter has
  its one attestation recorded verbatim in the JSON.
- `[1,126]` `2_Pass_Percentage` displays as its argument alone; whatever it computes,
  it is not visible in the rendering, which is exactly why it is refuse-only for SQL.

So the renderer takes **arity and fixity from this table**, and the **SQL function name
from the existing allowlist** (§6). Where the two disagree, the allowlist wins or the
formula is refused — never a guess.

### Notes on individual codes

- `[1,64]` `GREATEST` is **`[INFER]`**. It occurs in the dumps only in an `IOFormula`
  that has no `DisplayFormula`, so the aligned corpus does not contain it. Its name is
  Oracle's own; its fixity is not fitted and must not be assumed. Refuse-only.
- `[1,89]` `IS NULL`: four clean rows attest `postfixSpaced` (`a IS NULL`), but fourteen
  are anonymiser casualties (§11) and the degenerate `passthrough` shape also covers
  them, so the corpus does not separate the two. Refuse-only until the corpus is rebuilt.
- `[1,162]/[1,163]/[1,164]` `CASE`/`WHEN`/`ELSE` are `UNTESTED` — they never occur in a
  row whose other codes were settled first. Their rendering is nonetheless legible in the
  corpus (`CASE WHEN a THEN b WHEN ( c ) THEN d ELSE e END`) and the shapes `caseEnd`,
  `whenThen` and `unarySpaced` are already implemented in the fitter. 4.3 should settle
  them by widening the evidence rule, not by asserting them.
- `[1,137]/[1,138]/[1,139]/[1,140]/[1,189]/[1,192]` are the analytic-function family:
  38 uses, all from one workbook pattern,
  `FIRST_VALUE(x) OVER(PARTITION BY a,b ORDER BY  p , q )`. The spacing is
  under-determined from a single attesting pattern. **Refuse-only, and do not implement
  analytics from this evidence.**
- `[1,49]` and `[1,18]` are both `TRUNC`, `[1,11]` and `[1,47]` both `ROUND`, `[1,95]`
  and `[1,114]` both `-`. The code, not the name, is the identity.

### `[5,4]` — the audit's known unknown, now settled

`[5,4,"20011201000000"]` displays as `'01.12.01'`.

Fitted the same way as a shape and by the same standard: the whole fit was run once per
candidate format and each scored by **how many date-bearing rows the resulting shapes
reproduce**. `yy.mm.dd` reproduces **846**; `dd.mm.yy` 184; `mm.dd.yy` 35;
`yyyy.mm.dd`, `dd/mm/yyyy` and the raw payload **0**. The runners-up score above zero
only on dates whose day and year digits coincide.

**Not one of the 7 670 date literals carries a time component** — every payload ends
`000000`. So the six trailing digits are structural, and a renderer that drops them loses
nothing on this estate. It must still *check* them and refuse a non-midnight payload
rather than truncate silently.

The renderer must not emit `TO_DATE('01.12.01')` into SQL: a two-digit year with no
format mask depends on `NLS_DATE_FORMAT`. Emit an explicit mask, or a bind.

## 5. Character encoding — settled

Measured on the committed corpus:

- The file is **not valid UTF-8**. Reading it as UTF-8 corrupts it.
- All 62 distinct non-ASCII bytes lie in **0xC0–0xFF**. **Zero** bytes fall in 0x80–0x9F,
  the only range where cp1252 and latin1 disagree — so for this corpus the two encodings
  are byte-identical and the `latin1` read is exact.
- 827 rows carry a non-ASCII byte: 42 in `io_formula`, 827 in `display_formula`.
- The 42 io-side rows are the load-bearing ones. `[5,1,"Kcÿers"]` displays as `'Kcÿers'`
  — the same byte 0xFF on both sides of the pair. That is the `PRÉMIO` case: it occurs as
  a **string literal**, not only as an item name, and it survives byte-for-byte.

**Rule:** every read and write of the corpus, of a dump, and of any `.DIS` body is
`latin1`. `readFormulaCorpus` already does this. A comparison that decodes either side as
UTF-8 is not an exact-match comparison.

## 6. The target AST, and where the renderer lives

Emit **SQL directly from the token tree** (D-050). Do not re-parse `DisplayFormula`: it is
a display language and it is ambiguous — `NVL(R Com Tx Com Vig/100,0)` has a bare item
name containing spaces abutting an operator.

**Parenthesise every infix node unconditionally** (D-051). `((a) + (b))`. This removes the
operator-precedence problem entirely: precedence only matters when re-emitting
un-parenthesised infix. No precedence table is needed for any code. The cost is uglier
generated SQL, which is the right trade for a system whose failure mode is silently wrong
numbers.

Emit into the **existing AST and allowlist**, not a parallel path (D-054):

- `backend/src/lib/sql/formula-parser.ts` holds the validated security contract —
  `AGGREGATE_FUNCTIONS` (`:21`, five members), `SCALAR_FUNCTIONS` (`:29`), identifiers
  validated and quoted from metadata, every runtime value a bind, no string splicing.
- `ParsedFormula` is `{ sql, containsAggregate, referencedItems }` (`:235`).
  `containsAggregate` is load-bearing for the fan-trap planner and must be set from the
  token tree, not re-derived from the emitted text.

Per D-011/D-054 the renderer lives in `migrate/src/semantics/` (the directory does not
exist yet) and is exported from `@discoverer-neo/core`. **No new npm workspace.**

## 7. Dual storage

D-055: store **both** the token form and the compiled expression. Provenance enables
re-import, diffing and forensic work; the compiled form is what executes; and improving
the renderer must not require re-migrating.

**The pattern already exists — copy it.** `joins.predicate_formula`
(`migrate/src/db/schema.ts:565`) holds `EXPRESSIONS.EXP_FORMULA1` verbatim and cites
D-055 in its own docblock: the decomposed form drives execution, the token tree stays
beside it *"to re-decompose later without re-migrating"*. That is exactly the shape the
formula columns need.

They do not have it. Each has one column, and it holds the token string:

| Table | Column | Holds today | Needs |
| --- | --- | --- | --- |
| `items` | `formula` (`text`, `:469`) | token string | + `formula_tokens` |
| `map_calculated_fields` | `formula` (`text`, `:1002`) | token string | + `formula_tokens` |
| `joins` | `predicate_formula` (`text`, `:565`) | token string | already correct |

`backend/src/services/formula-bucket.ts` detects the `[class,id]` shape and quarantines
it, which is why 49 782 of 49 819 stored formulas sit in `QUARANTINED` today.

**So 4.2 adds a column, it does not overwrite one.** Add `formula_tokens text` beside each
`formula`, copy the existing value into it, and let `formula` become the compiled
expression. Overwriting `formula` in place would destroy the only copy of the source token
string — the one thing a re-render needs.

## 8. Calculation references expand recursively

D-056. A `[6,n]` leaf is *sometimes another calculation*, and Oracle's own dump tool
substitutes that calculation's **formula** in its place rather than its name
(`workbook-parser.ts:3053-3064`). The corpus shows this directly: identifier placeholders
that must swallow brackets and commas, which is why the fitter needs a `loose` placeholder
class at all. WB-04's 2 536 "disagreements" are that unwalked chain, and they are **by
design, not defects**.

- Expand **at render time**, not at migration time, so improving the renderer does not
  require re-migrating.
- **Cycle detection is mandatory.** A cycle is a refusal with a stated reason, never a
  recursion limit that silently truncates.
- The corpus's identifier map is keyed by identifier text and is globally stable, so
  chains still resolve in the anonymised corpus and 4.4's gate is meaningful.

## 9. Custom functions `[2,n]` — the corpus cannot help

**The aligned corpus contains zero `[2,n]` occurrences.** Measured:
`grep -c '\[2,' formula-corpus.tsv` returns 0 across all 22 748 rows.

`formula-decoder-analysis.md` counts 7 097 `[2,n]` uses over the whole dump set. Both are
right and they answer different questions: that count is over every token string anywhere
in the 547 dumps, while the corpus harvests only `EulPrivateItem` and `EulPrivateFilter`
entries that have **both** an `IOFormula` and a `DisplayFormula`. Every `[2,n]` use in
this estate falls outside that intersection.

Consequences, and they are hard ones:

- **There is no aligned evidence for how Oracle renders a custom-function call.** 4.3
  cannot fit it from the committed corpus. Its shape (`NAME(args)`) is a reasonable
  reading of Oracle's SQL, but it is an inference and must be labelled `[INFER]`.
- D-057's requirement stands: `[2,n]` resolves through the workbook element table to a
  migrated `custom_functions` row, or the formula is refused. 593 functions are migrated;
  the analysis counts ~100 actually referenced.
- Security: the resolved name is an identifier from metadata, validated and quoted. Never
  spliced. A `[2,n]` that does not resolve is a refusal, not a pass-through.

## 10. The refusal policy

Inherited and non-negotiable (D-058). The parser's established instinct is to **refuse
rather than approximate** — `NOT IN` maps to `null` rather than to `IN`, because
migrating it as `IN` inverts the filter. That instinct is why this estate's numbers can be
trusted at all.

Refuse, with a stated reason, on:

| Reason | Trigger |
| --- | --- |
| `UNFITTED_CODE` | any `[1,n]` whose table state is not `FITTED` — including `[1,64]` |
| `UNKNOWN_NODE` | any node the parser typed `unknown` |
| `UNRESOLVED_FUNCTION` | a `[2,n]` with no migrated `custom_functions` row |
| `UNRESOLVED_ELEMENT` | a `[6,n]`/`[8,n]` the element table does not carry |
| `DATE_WITH_TIME` | a `[5,4]` payload not ending `000000` |
| `CALC_CYCLE` | a calculation-reference cycle |
| `UNREAGGREGABLE` | an aggregate the fan-trap planner cannot re-aggregate — `AVG`, `COUNT DISTINCT`, `STDDEV`, `VARIANCE` |
| `NOT_IN_ALLOWLIST` | a fitted code whose SQL name is outside `AGGREGATE_FUNCTIONS ∪ SCALAR_FUNCTIONS` |

**Never silently substitute a near-equivalent function.** A quarantined formula is a
visible gap; a wrongly-rendered one is a wrong number in a report whose users have fifteen
years of trained trust in it.

Aggregates present in the aligned corpus, for scale: `SUM` 781, `COUNT` 23,
`COUNT_DISTINCT` 3 — 403 rows, 806 weighted uses. `AVG`, `STDDEV` and `VARIANCE` do not
occur in the aligned corpus at all.

## 11. What the evidence cannot tell you

Three limits. All three are measured, and none of them is a reason to guess.

### 11.1 The anonymiser damaged 917 rows (4.03 %, 1 456 occurrences)

A Discoverer **private filter's `Name` is frequently its own `DisplayFormula` verbatim**
— the shipped test fixture shows exactly that (`d4wkdmp-dump-parser.test.ts:46-53`). So
Phase 0.5's identifier map registered whole display strings as single identifiers and
replaced them wholesale, byte-class- and length-preserving. Oracle's own keywords were
destroyed while the punctuation survived:

```
[1,98]([1,81]([6,18],[5,2,"2009"]),[1,81]([6,19],[5,2,"981"]))
  => Dqo Urmmoqhb = 8472 ZCK Insrhltd = 532      -- 'AND' became 'ZCK', '2009' became '8472'
[1,89]([6,40])
  => Nehk Hagt BU EXOQ                            -- 'IS NULL' became 'BU EXOQ'
```

Detected two ways — a literal has gone missing (188 rows) or a word-shaped built-in name
has (802 rows) — and excluded from evidence. Some damage is **undetectable**: a row built
only from identifiers and symbol operators can be overwritten and still look well-formed.
That is why the settling rule discounts rows no hypothesis can explain (§3).

**This bounds Phase 4.2's `>= 93 %` and 4.3's `>= 99 %` exact-match gates.** A damaged row
can never match, so the achievable ceiling on the committed corpus is about **96 %** by
distinct rows. Either state the gates against the clean subset, or rebuild the corpus.

**The fix, for whoever next has `d4dumps/`:** exclude a private filter's `Name` from the
identifier map when it is equal to that entry's `DisplayFormula`, and re-run
`npm run rebuild-corpus`. Everything else about D-114 stands.

### 11.2 The 7 371 unrendered `IOFormula` entries are not classified here

Bounded, not settled. What is established without the dumps:

- Only two entry kinds carry these fields at all — `EulPrivateItem` (calculations) and
  `EulPrivateFilter` (conditions) — so all 7 371 are one of those two.
- **"They are conditions" is refuted.** Private filters do carry a `DisplayFormula`, and
  fitted condition operators (`=` 1 036 uses, `LIKE` 839, `BETWEEN` 561, `IN` 363) come
  from aligned condition rows.
- Every `[2,n]` in the estate is inside this remainder (§9), which is a substantive part
  of the answer.

`d4dumps/` is **not present on this machine** — 547 dumps and their `.DIS` sources are
gone; only Oracle's own demo workbooks remain in `DISCVR4/`. So the classification cannot
be run. `build-formula-corpus.ts` now counts the remainder by
`PrivateItem/calc | PrivateItem/notCalc | PrivateFilter` × `absent | empty` and writes it
to `formula-corpus.meta.json` as `ioWithoutDisplayByKind`. **One rebuild on a machine with
the dumps answers open question 1 outright.** Until then it is open, and this stage does
not pretend otherwise.

### 11.3 Twelve codes never met settled company

`UNTESTED` is not `CONTRADICTED`. Those twelve codes carry 445 uses and simply never
appeared in a row whose other codes were already fitted — `CASE`/`WHEN`/`ELSE` block each
other, and the analytic family occurs only inside one another. Widening the evidence rule
(fit a *pair* of unknown codes jointly) would settle most of them and is the cheapest win
available to 4.3.

**Phase 4.2 swaps `NO_RENDERER` for the real renderer and raises the baseline. That is the
whole mechanism.** Two rates, and a gate must say which it means: the **distinct** rate is
how much of the formula language is covered; the **weighted** rate is how many real
formulas in a real estate would render.

The compile gate stays the D-059 four-bucket partition —
`COMPILED` / `COMPILED_UNVERIFIED` / `QUARANTINED(reason)` / `FAILED` — with CI asserting
`FAILED = 0`. It lives in `migrate/src/services/migration-verify.ts` (seam 2) with the
classifier in `backend/src/services/formula-bucket.ts`; **not** in `diff-corpus.ts`, which
needs a live Oracle and uncommitted dumps and can never run in CI. `COMPILED` stays
unreachable until the Phase 9.1 Oracle contract tests exist: nothing may claim a formula
works until something has run it. Baseline today: 0 / 37 / 49 782 / 0 over 49 819.
