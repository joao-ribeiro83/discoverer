# Oracle Discoverer 4.1 End User Layer (EUL4) Metadata Reference

> **Purpose:** Working reference for a migration application that needs to inspect, understand, and potentially migrate Oracle Discoverer 4.1 EUL metadata.

## Scope and provenance

This document consolidates the discussion about the Oracle Discoverer 4.1 / 4i End User Layer (EUL), with emphasis on:

- EUL4 database tables and their logical roles.
- Business Area → Folder → Item relationships.
- Joins, expressions, LOVs/item classes, hierarchies, functions, summaries, workbooks and execution statistics.
- The relationship between EUL metadata and SQL generated by Discoverer.
- Queries useful for reverse-engineering an actual EUL4 installation.
- Important differences between a logical EUL relationship and an Oracle-enforced foreign key.
- Caveats around using EUL5 documentation to infer EUL4 structure.

### Important qualification

Oracle's public Discoverer 4.1 manuals document the logical EUL architecture and provide official EUL Status Workbooks, but they do not provide a complete, authoritative public column-by-column dictionary for every EUL4 table.

Therefore:

- Use the relationships explicitly documented or demonstrated in EUL4 examples as the primary reference.
- Treat undocumented column names and relationships as implementation evidence that should be verified against the target EUL4 schema.
- Do **not** assume that every logical relationship is enforced by an Oracle `FOREIGN KEY` constraint.
- Do **not** blindly transpose an EUL5 schema to EUL4.

# 1. EUL Architecture

Discoverer uses the EUL as a semantic metadata layer between end-user workbooks and the Oracle database.

Conceptually:

```text
                         DISCOVERER 4.1
                               |
                               | user selections
                               v
                         WORKBOOK / SHEET
                               |
                         +-----+------+
                         |            |
                         v            v
                      Folders      Conditions
                         |
                         v
                       Items
                         |
                  +------+-------+
                  |      |       |
                  v      v       v
              Expressions Joins  LOVs
                  |       |
                  |       v
                  |    Key constraints
                  |
                  v
           Database object metadata
          (table/view/column/expression)
                  |
                  v
             SQL generator
                  |
                  v
          Oracle application DB
```

The key idea for a migration application is:

> **The EUL normally stores the semantic metadata from which Discoverer generates SQL; it is not simply a table containing one canonical SQL statement for every report.**

# 3. Business Areas

## `EUL4_BAS`

This is the master Business Area table.

Important fields commonly encountered include:

```text
BA_ID
BA_NAME
...
```

A Business Area can be viewed as the top-level semantic container exposed to users.

## `EUL4_BA_OBJ_LINKS`

This is the association between Business Areas and folders/objects.

Important relationships:

```text
EUL4_BA_OBJ_LINKS.BOL_BA_ID
        |
        +----> EUL4_BAS.BA_ID

EUL4_BA_OBJ_LINKS.BOL_OBJ_ID
        |
        +----> EUL4_OBJS.OBJ_ID
```

Conceptually:

```text
EUL4_BAS
   |
   | BA_ID
   v
EUL4_BA_OBJ_LINKS
   |
   | BOL_OBJ_ID
   v
EUL4_OBJS
```

The association table can also contain ordering information for folders within the Business Area.

### Example

```sql
SELECT DISTINCT
       ba.ba_id,
       ba.ba_name,
       obj.obj_id,
       obj.obj_name,
       obj.obj_type
FROM   eul4_bas ba
       JOIN eul4_ba_obj_links bol
         ON bol.bol_ba_id = ba.ba_id
       JOIN eul4_objs obj
         ON obj.obj_id = bol.bol_obj_id
ORDER BY
       ba.ba_name,
       obj.obj_name;
```

# 4. Folders and Objects

## `EUL4_OBJS`

`EUL4_OBJS` is one of the central EUL tables.

Commonly encountered fields include:

```text
OBJ_ID
OBJ_NAME
OBJ_DEVELOPER_KEY
OBJ_DESCRIPTION
OBJ_TYPE
...
```

It holds folder/object-level metadata.

The object type identifies the sort of Discoverer object represented by the row. Exact type codes should be interpreted using the target 4.1 EUL rather than assumed from a later version.

# 5. Items and Expressions

## `EUL4_EXPRESSIONS`

This is the key metadata table for folder items and expressions.

Important fields encountered in EUL4 material include:

```text
EXP_ID
EXP_NAME
EXP_DEVELOPER_KEY
EXP_DESCRIPTION
EXP_DATA_TYPE
EXP_SEQUENCE
EXP_CREATED_DATE
EXP_UPDATED_DATE

IT_OBJ_ID
IT_FUN_ID
IT_DOM_ID
IT_HEADING
IT_HIDDEN
IT_PLACEMENT
IT_FORMAT_MASK
IT_MAX_DATA_WIDTH
```

The most important relationship is:

```text
EUL4_EXPRESSIONS.IT_OBJ_ID
        |
        +----> EUL4_OBJS.OBJ_ID
```

This means:

```text
Business Area
    ↓
Folder
    ↓
EUL4_OBJS
    ↓
EUL4_EXPRESSIONS
    ↓
Item
```

### Item expression types

EUL4 examples distinguish database-backed items and created/calculated items using expression type values such as:

```text
CO  = database/object item
CI  = created/calculated or complex item
```

The exact set of codes should be taken from the installed EUL4 schema/status workbooks.

### Example query

```sql
SELECT
       ba.ba_name,
       obj.obj_id,
       obj.obj_name AS folder_name,
       exp.exp_id,
       exp.exp_name,
       exp.exp_developer_key,
       exp.exp_type,
       exp.exp_description,
       exp.exp_data_type,
       exp.it_heading,
       exp.it_hidden,
       exp.it_sequence
FROM   eul4_bas ba
       JOIN eul4_ba_obj_links bol
         ON bol.bol_ba_id = ba.ba_id
       JOIN eul4_objs obj
         ON obj.obj_id = bol.bol_obj_id
       JOIN eul4_expressions exp
         ON exp.it_obj_id = obj.obj_id
WHERE  obj.obj_name = :folder_name
ORDER BY
       exp.exp_sequence;
```

# 6. Item Classes / LOVs

## `EUL4_DOMAINS`

`EUL4_DOMAINS` contains domain/item-class/LOV-related metadata.

Key relationship:

```text
EUL4_EXPRESSIONS.IT_DOM_ID
        |
        +----> EUL4_DOMAINS.DOM_ID
```

Example:

```sql
SELECT
       ba.ba_name,
       obj.obj_name       AS folder_name,
       exp.it_heading     AS item_heading,
       dom.dom_id,
       dom.dom_name       AS item_class
FROM   eul4_bas ba
       JOIN eul4_ba_obj_links bol
         ON bol.bol_ba_id = ba.ba_id
       JOIN eul4_objs obj
         ON obj.obj_id = bol.bol_obj_id
       JOIN eul4_expressions exp
         ON exp.it_obj_id = obj.obj_id
       LEFT JOIN eul4_domains dom
         ON dom.dom_id = exp.it_dom_id
ORDER BY
       ba.ba_name,
       obj.obj_name,
       exp.it_heading;
```

# 7. Functions

Function metadata is represented by a group of tables:

```text
EUL4_FUNCTIONS
    |
    +--- EUL4_FUN_ARGUMENTS
    |
    +--- EUL4_FUN_CTGS
    |
    +--- EUL4_FUN_FC_LINKS
```

Expression-to-function relationship:

```text
EUL4_EXPRESSIONS.IT_FUN_ID
        |
        +----> EUL4_FUNCTIONS.FUN_ID
```

This allows Discoverer items to reference registered/custom functions rather than being limited to simple column references.

# 8. Joins and Key Constraints

## `EUL4_KEY_CONS`

This is one of the most important tables when reverse-engineering generated SQL.

The logical relationship is:

```text
EUL4_OBJS
    |
    +--------------------+
                         |
                         v
                 EUL4_KEY_CONS
                         |
                         +--------------------+
                                              |
                                              v
                                          EUL4_OBJS
```

Important object references found in EUL material include:

```text
KEY_OBJ_ID
FK_OBJ_ID_REMOTE
```

These identify the folder/object sides of a join/key relationship.

Conceptually:

```text
Folder A
   |
   +--- KEY_OBJ_ID
          EUL4_KEY_CONS
   +--- FK_OBJ_ID_REMOTE
   |
Folder B
```

which can result in SQL such as:

```sql
FROM   folder_A a,
       folder_B b
WHERE  a.customer_id = b.customer_id
```

The critical point is that the EUL stores the semantic relationship. Discoverer turns that metadata into executable SQL.

---

# 9. Expression and Object Dependencies

Important support tables include:

```text
EUL4_EXP_DEPS
EUL4_OBJ_DEPS
EUL4_OBJ_JOIN_USGS
```

They are used to track dependencies among semantic objects and expressions.

This matters for migration because a calculated item may depend on other items, which themselves depend on folders or expressions.

A migration tool should therefore not treat `EUL4_EXPRESSIONS` as a flat independent list.

---

# 10. Segmented Metadata

## `EUL4_SEGMENTS`

Large metadata/expression content may be segmented.

Frequently encountered fields include:

```text
SEG_CUO_ID
SEG_SEQUENCE
SEG_CHUNK1
SEG_CHUNK2
SEG_CHUNK3
SEG_CHUNK4
```

Conceptually:

```text
EUL object
   |
   +--> EUL4_SEGMENTS
            |
            +--> segment 1
            +--> segment 2
            +--> segment 3
            +--> ...
```

An example reconstruction pattern is:

```sql
SELECT o.obj_name,
       s.seg_chunk1 ||
       s.seg_chunk2 ||
       s.seg_chunk3 ||
       s.seg_chunk4 AS metadata_text
FROM   eul4_objs o
       LEFT OUTER JOIN eul4_segments s
         ON o.obj_id = s.seg_cuo_id
ORDER BY
       o.obj_name,
       s.seg_sequence;
```

The exact interpretation of a segment depends on the metadata structure that owns it.

# 11. Hierarchies

Hierarchy-related tables include:

```text
EUL4_HIERARCHIES
EUL4_HI_NODES
EUL4_HI_SEGMENTS
EUL4_IG_EXP_LINKS
EUL4_IHS_FK_LINKS
```

Conceptually:

```text
Hierarchy
    |
    +--- Levels / Nodes
             |
             +--- Expressions
             |
             +--- Folder relationships
```

For example:

```text
Year
 └── Quarter
      └── Month
           └── Day
```

Hierarchy metadata can influence grouping and drill operations and therefore affect generated SQL and worksheet behavior.

---

# 12. Conditions

Conditions are another semantic metadata layer.

They can ultimately become SQL predicates such as:

```sql
WHERE status = 'OPEN'
```

The important conceptual chain is:

```text
Discoverer condition
        ↓
semantic expression/predicate
        ↓
worksheet query
        ↓
SQL WHERE clause
```

Do not assume the stored condition itself is necessarily identical to the final generated SQL fragment.

---

# 13. Summary Management

Important summary-related tables include:

```text
EUL4_SUMMARY_OBJS
EUL4_SUMO_EXP_USGS
EUL4_SUM_BITMAPS
EUL4_SUM_RFSH_SETS
EUL4_ASM_POLICIES
EUL4_ASMP_CONS
EUL4_ASMP_LOGS
```

Their purpose is to support Discoverer's aggregate/summary management.

A migration application must preserve summary metadata if the target environment depends on summary-aware query generation.

# 14. Workbooks / Documents

## `EUL4_DOCUMENTS`

Important fields commonly exposed include:

```text
DOC_ID
DOC_NAME
DOC_DEVELOPER_KEY
DOC_CREATED_BY
...
```

Example:

```sql
SELECT
       doc_id,
       doc_name,
       doc_developer_key,
       doc_created_by
FROM   eul4_documents
ORDER BY doc_name;
```

This identifies saved Discoverer workbooks/documents.

## Critical distinction

`EUL4_DOCUMENTS` should **not** be treated as a simple "report SQL" table.

The actual relationship is closer to:

```text
Saved workbook
      ↓
EUL4_DOCUMENTS
      ↓
serialized/structured workbook definition
      ↓
worksheet selections
      ↓
EUL semantic objects
      ↓
runtime SQL generation
```

The workbook definition and the semantic EUL metadata must therefore be separated in a migration design.

# 20. EUL Metadata → Generated SQL

| `EUL4_BA_OBJ_LINKS` | Determines which folders belong to the BA |

| `EUL4_KEY_CONS` | Supplies join relationships |
| `EUL4_EXP_DEPS` | Resolves calculated expression dependencies |
| `EUL4_DOMAINS` | Supplies LOV/item-class semantics |

| Summary metadata | Allows summary objects to be considered in query generation |
| `EUL4_DOCUMENTS` | Identifies saved workbook/document definitions |

# 21. Where Specific Discoverer Information Lives

| Administrator question | Primary EUL4 area |
|---|---|
| Where is a Business Area? | `EUL4_BAS` |
| Which folders are in a Business Area? | `EUL4_BA_OBJ_LINKS` + `EUL4_OBJS` |
| Where is a folder definition? | `EUL4_OBJS` |
| Where are the folder's items? | `EUL4_EXPRESSIONS` |
| Where is an item class/LOV? | `EUL4_DOMAINS` |
| Where is a custom/calculated function? | `EUL4_FUNCTIONS*` + expression/dependency metadata |
| Why are two folders joined? | `EUL4_KEY_CONS` + `EUL4_OBJS` |
| What does a calculated item depend on? | `EUL4_EXP_DEPS` |
| Where are hierarchy definitions? | `EUL4_HIERARCHIES`, `EUL4_HI_NODES`, `EUL4_HI_SEGMENTS` |
| Where is a saved workbook? | `EUL4_DOCUMENTS` and related workbook structures |
| Where is query execution history/statistics? | `EUL4_QPP_STATS` |
| Where is batch reporting metadata? | `EUL4_BATCH_*` |
| Where is EUL security? | `EUL4_EUL_USERS`, `EUL4_ACCESS_PRIVS` |

# 22. Important PK/FK Caveat

The term "foreign key" must be used carefully.

Discoverer EUL schemas historically use many application-managed relationships. A relationship such as:

```text
EUL4_BAS.BA_ID
       ↑
       |
EUL4_BA_OBJ_LINKS.BOL_BA_ID
```

may be a **logical foreign key** even when there is no Oracle-enforced `FOREIGN KEY` constraint.

For migration documentation, distinguish:

```text
Physical PK constraint
Logical PK/identifier
Physical FK constraint
Logical FK/reference
```

This prevents a migration tool from incorrectly assuming that every semantic reference is an Oracle constraint.

# 23. How to Inspect the Actual EUL4 Schema

Run these queries as the EUL owner (or against the EUL schema with sufficient privileges).

## 23.1 All EUL4 tables

```sql
SELECT table_name
FROM   user_tables
WHERE  table_name LIKE 'EUL4_%'
ORDER BY table_name;
```

## 23.2 Actual primary keys

```sql
SELECT
    acc.table_name,
    acc.constraint_name,
    acc.column_name,
    acc.position
FROM user_cons_columns acc
JOIN user_constraints ac
  ON ac.constraint_name = acc.constraint_name
 AND ac.table_name      = acc.table_name
WHERE ac.constraint_type = 'P'
AND   acc.table_name LIKE 'EUL4_%'
ORDER BY
    acc.table_name,
    acc.position;
```

## 23.3 Actual foreign keys

```sql
SELECT
    a.table_name              AS child_table,
    a.constraint_name,
    a.column_name             AS child_column,
    c_pk.table_name           AS parent_table,
    b.column_name             AS parent_column,
    a.position
FROM user_cons_columns a
JOIN user_constraints c
  ON c.constraint_name = a.constraint_name
 AND c.table_name      = a.table_name
JOIN user_constraints c_pk
  ON c.r_constraint_name = c_pk.constraint_name
JOIN user_cons_columns b
  ON b.constraint_name = c_pk.constraint_name
 AND b.position        = a.position
WHERE c.constraint_type = 'R'
AND   a.table_name LIKE 'EUL4_%'
ORDER BY
    a.table_name,
    a.constraint_name,
    a.position;
```

## 23.4 All columns

```sql
SELECT
    table_name,
    column_id,
    column_name,
    data_type,
    data_length,
    nullable
FROM user_tab_columns
WHERE table_name LIKE 'EUL4_%'
ORDER BY
    table_name,
    column_id;
```

These queries are the authoritative starting point for the physical schema of a specific EUL4 installation.

# 24. High-Value Reverse-Engineering Queries

## 24.1 Business Area → Folder → Item

```sql
SELECT
    ba.ba_name                              AS business_area,
    obj.obj_name                            AS folder,
    obj.obj_developer_key                   AS folder_key,
    exp.exp_name                            AS item,
    exp.exp_developer_key                   AS item_key,
    exp.exp_type,
    exp.exp_data_type,
    exp.it_heading,
    exp.it_hidden,
    exp.it_sequence,
    exp.it_format_mask,
    dom.dom_name                            AS item_class,
    fun.fun_name                            AS function_name
FROM eul4_bas ba
JOIN eul4_ba_obj_links bol
  ON bol.bol_ba_id = ba.ba_id
JOIN eul4_objs obj
  ON obj.obj_id = bol.bol_obj_id
JOIN eul4_expressions exp
  ON exp.it_obj_id = obj.obj_id
LEFT JOIN eul4_domains dom
  ON dom.dom_id = exp.it_dom_id
LEFT JOIN eul4_functions fun
  ON fun.fun_id = exp.it_fun_id
ORDER BY
```

# 26. EUL4 vs EUL5 Warning

Discoverer documentation often refers to EUL4 and EUL5.

For a Discoverer 4.1 migration project:

```text
Discoverer 4.1 → EUL4_*
```

should be treated independently from:

```text
Later Discoverer → EUL5_*
```

A migration tool should never assume that:

```text
EUL5_TABLE
```

maps mechanically to:

```text
EUL4_TABLE
```

without verifying the installed 4.1 schema.

Oracle's upgrade documentation describes migration from earlier EUL versions into later EUL structures, which confirms that the physical schema changed between releases.

# 28. Migration Strategy

A sensible migration process is:

```text
1. Inventory physical EUL4 schema
       ↓
2. Extract Business Areas
       ↓
3. Extract folders
       ↓
4. Extract folder/BA associations
       ↓
5. Extract items/expressions
       ↓
6. Extract domains/LOVs
       ↓
7. Extract joins/key constraints
       ↓
8. Extract calculated-expression dependencies
       ↓
9. Extract hierarchies
       ↓
10. Extract conditions
       ↓
11. Extract summary metadata
       ↓
12. Extract workbooks/documents
       ↓
13. Decode worksheet/query definitions
       ↓
14. Resolve workbook → EUL object references
       ↓
15. Reconstruct semantic query model
       ↓
16. Generate target SQL/query definitions
       ↓
17. Validate generated SQL against source SQL/results
```

The order matters because workbooks depend upon the semantic layer; it is risky to start with `EUL4_DOCUMENTS` alone.

# 29. Migration Validation Rules

Recommended validation checks:

### Business Area integrity

For every Business Area:

```text
BA_ID is unique
BA_NAME is preserved
Every linked folder exists
```

### Folder integrity

```text
OBJ_ID is unique
Every BA association references an existing OBJ_ID
Object type is understood
```

### Item integrity

```text
EXP_ID is unique
Every IT_OBJ_ID references an existing folder/object
Every IT_DOM_ID resolves when non-null
Every IT_FUN_ID resolves when non-null
```

### Join integrity

```text
Every referenced KEY_OBJ_ID exists
Every referenced FK_OBJ_ID_REMOTE exists
No orphaned join objects
```

### Workbook integrity

```text
Every referenced EUL object exists
Every worksheet can resolve its folder/item references
Every workbook owner exists
```

### Query integrity

For each migrated workbook/query:

```text
Source semantic objects
        ==
Target semantic objects

Generated SQL:
  - same tables/objects
  - same joins
  - equivalent predicates
  - equivalent projections
  - equivalent calculated expressions
```

# 31. Key Conclusions for the Migration Application

1. **`EUL4_BAS`, `EUL4_BA_OBJ_LINKS`, `EUL4_OBJS`, and `EUL4_EXPRESSIONS` form the core Business Area → Folder → Item model.**

2. **`EUL4_KEY_CONS` is central to explaining why Discoverer generates particular joins.**

3. **`EUL4_DOMAINS` and `EUL4_FUNCTIONS*` add semantic behaviour to items.**

4. **Expression/object dependency tables matter for reconstructing calculated items.**

5. **`EUL4_DOCUMENTS` identifies saved workbooks but should not be treated as a plain SQL repository.**

6. **Generated SQL is a runtime result of workbook selections + EUL semantic metadata + Discoverer query generation.**

7. **`EUL4_QPP_STATS` is an execution/history source, not the canonical report definition.**

8. **Not every logical relationship is necessarily an Oracle-enforced foreign key.**

9. **The exact physical schema should always be extracted from the target EUL4 database.**

10. **The Oracle 4.1 EUL Status Workbooks (`EUL4.eex` / `EUL4.sql`) are one of the most valuable authoritative resources for validating the metadata model.**

# 33. Next Step for a Site-Specific EUL4 Dictionary

For a production-quality migration reference, collect the following from the Discoverer 4.1 EUL owner:

```sql
SELECT table_name
FROM   user_tables
WHERE  table_name LIKE 'EUL4_%'
ORDER BY table_name;
```

```sql
SELECT
    acc.table_name,
    acc.constraint_name,
    acc.column_name,
    acc.position
FROM user_cons_columns acc
JOIN user_constraints ac
  ON ac.constraint_name = acc.constraint_name
 AND ac.table_name      = acc.table_name
WHERE ac.constraint_type = 'P'
AND   acc.table_name LIKE 'EUL4_%'
ORDER BY
    acc.table_name,
    acc.position;
```

```sql
SELECT
    a.table_name              AS child_table,
    a.constraint_name,
    a.column_name             AS child_column,
    c_pk.table_name           AS parent_table,
    b.column_name             AS parent_column,
    a.position
FROM user_cons_columns a
JOIN user_constraints c
  ON c.constraint_name = a.constraint_name
 AND c.table_name      = a.table_name
JOIN user_constraints c_pk
  ON c.r_constraint_name = c_pk.constraint_name
JOIN user_cons_columns b
  ON b.constraint_name = c_pk.constraint_name
 AND b.position        = a.position
WHERE c.constraint_type = 'R'
AND   a.table_name LIKE 'EUL4_%'
ORDER BY
    a.table_name,
    a.constraint_name,
    a.position;
```

```sql
SELECT
    table_name,
    column_id,
    column_name,
    data_type,
    data_length,
    nullable
FROM user_tab_columns
WHERE table_name LIKE 'EUL4_%'
ORDER BY
    table_name,
    column_id;
```

With those four result sets, a migration-specific EUL4 dictionary can be generated with:

- every actual table in the installation;
- every column;
- exact physical PK/FK constraints;
- logical FK references;
- Business Area/folder/item lineage;
- workbook/worksheet lineage;
- expression dependencies;
- join lineage;
- and a report-oriented SQL reconstruction map.
